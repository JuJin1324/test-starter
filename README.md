# Test Starter

> 일반적으로 소프트웨어 테스트는 다음과 같은 단계(또는 레벨)로 구분할 수 있어. 마치 작은 것부터 점점 크게 확인해 나가는 과정이라고 생각하면 돼.

### 단위 테스트 (Unit Testing)

> * 테스트 대상: 가장 작은 코드 단위 (함수, 메서드, 클래스, 모듈 등).
> * 주요 수행자: 개발자 (Developer).
> * 검증 목적: 각 코드 단위가 독립적으로 의도된 대로 정확하게 작동하는지 검증. 특정 입력에 대해 예상된 출력을 반환하는지, 예외 처리는 잘 되는지 등을 확인.
> * 특징:
> * 가장 작은 범위를 테스트하며, 매우 빠르게 실행됨.
> * 다른 컴포넌트와의 의존성은 보통 Mock 객체나 Stub을 사용하여 격리시킴.
> * 코드 수준의 논리적 오류를 조기에 발견하는 데 효과적.
> * 자동화가 필수적 (예: JUnit, pytest 등).

### 통합 테스트 (Integration Testing)

> * 테스트 대상: 단위 테스트를 통과한 모듈(컴포넌트)들을 **결합(통합)**한 부분. 모듈 간의 상호작용 및 인터페이스.
> * 주요 수행자: 개발자 또는 통합 테스터.
> * 검증 목적: 여러 모듈이 함께 작동할 때 발생하는 문제를 검증. 모듈 간의 데이터 전달, API 호출, 통신 등이 원활하게 이루어지는지 확인.
>
> 특징:
> * 단위 테스트보다 더 넓은 범위를 테스트.
> * 실제 데이터베이스, 외부 API 연동 등을 포함할 수 있음.
> * 모듈 간 인터페이스 오류나 데이터 형식 불일치 등을 발견하는 데 중점.
> * 단위 테스트보다 실행 시간이 오래 걸릴 수 있음.

### 시스템 테스트 (System Testing)

> * 테스트 대상: 완전히 통합된 전체 시스템 (애플리케이션 전체).
> * 주요 수행자: 독립적인 테스터 (QA 팀 등). 개발자와 다른 관점에서 테스트.
> * 검증 목적: 통합된 시스템이 **명세된 요구사항(기능적/비기능적 요구사항)**을 만족하는지 검증. 사용자의 관점에서 시스템 전체의 동작을 확인.
>
> 특징:
> * 블랙박스 테스트 관점에서 수행되는 경우가 많음 (내부 구조보다는 입/출력과 기능 동작에 집중).
> * 실제 운영 환경과 유사하게 구성된 테스트 환경에서 수행됨.
> * 기능 요구사항 검증: 모든 기능이 요구사항 명세서대로 동작하는가?
> * 비기능 요구사항 검증: 성능(응답 시간, 처리량), 보안(취약점), 사용성(편의성), 신뢰성(안정성), 부하(스트레스) 등을 테스트.
> * End-to-End 시나리오를 테스트.

### 인수 테스트 (Acceptance Testing)

> * 테스트 대상: 완전히 통합된 전체 시스템. (시스템 테스트와 동일)
> * 주요 수행자: 실제 사용자, 고객 또는 비즈니스 분석가. (QA팀이 지원할 수 있음)
> * 검증 목적: 개발된 시스템이 실제 사용자의 요구사항과 비즈니스 목표를 충족하는지, 그래서 사용자가 시스템을 "인수(Accept)"할 수 있는지 최종적으로 검증.
>
> 특징:
> * 사용자 관점에서의 테스트가 핵심. "이 시스템이 우리가 원했던 문제를 해결해 주는가?", "실제 업무에 사용할 수 있는가?"를 판단.
> * 시스템 테스트가 "요구사항 명세대로 만들어졌는가?"에 가깝다면, 인수 테스트는 "그래서 쓸만한가? 우리 목적에 부합하는가?"에 가까움.
> * 실제 데이터를 사용하거나 실제 사용 환경에서 테스트하는 경우가 많음.
>
> 종류:
> * 사용자 인수 테스트 (UAT - User Acceptance Testing): 실제 사용자가 직접 시스템을 사용해보며 요구사항 충족 여부 확인.
> * 비즈니스 인수 테스트 (BAT - Business Acceptance Testing): 시스템이 비즈니스 목표와 프로세스를 만족하는지 확인.
> * 계약 인수 테스트 (CAT - Contract Acceptance Testing): 계약서에 명시된 인수 기준을 만족하는지 확인.
> * 알파/베타 테스트: 출시 전 제한된 사용자(알파) 또는 불특정 다수(베타)에게 시스템을 공개하여 피드백을 받는 테스트.
